# Business calendar setup

Requirements checklist: owner/admin authorization; company-named calendar in company time zone; real owner OAuth with calendar.app.created; existing calendar selection preserved; read/create/update/delete appointment-event permission; no whole-calendar delete control; durable intent before provider call; repeat-click/ambiguous-result guards; no automatic calendar switching; internal-only setup; explicit personal-calendar limitation; future busy-only multi-calendar design.

After connecting Google, owner can load existing owned calendars or create a separate business calendar named “Business name — Appointments.” Creation is recorded before the single provider POST. A repeated request returns the existing result; an uncertain/crashed result is not retried automatically. Owner can recover by finding the calendar in Google Calendar, loading calendars and selecting it. A definite Google rejection allows retry. Creation itself does not select the calendar or migrate existing appointments. Existing connections without calendar.app.created may keep using their selected calendar; creating one requires reconnect and renewed consent.

Keep personal events on personal calendars and customer appointments on the selected business calendar. Currently only that selected calendar is checked by the CRM. Owner uses Block time to reserve personal commitments; public availability excludes that time without a personal reason. Displaying several calendars together in Google Calendar does not combine their availability in the CRM.

Future implementation (not active): separate writable business calendar from opt-in busy-only calendars; request the least permission needed; store selected source IDs per tenant; union all busy intervals with CRM blocks/travel buffers; fail closed when any required source cannot be checked; recheck at hold/approval; retain transaction capacity constraints. Personal event names/descriptions/attendees must not be fetched, stored or shown to customers. Test time zones/DST, recurring/all-day/moved events, access revocation, stale snapshots and overlapping sources.

Live acceptance remains required: owner consent, actual calendar creation, calendar ownership/time zone, read/create/update/delete of a synthetic event, selection/save and blocked-time behavior. Synthetic tests do not certify provider success or overall production readiness.
